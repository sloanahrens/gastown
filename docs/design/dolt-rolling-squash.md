# Rolling Dolt history squash

Status: design and first-run runbook (gt-2conu). Nothing here is implemented. The operator approved, on 2026-11-01, a guarded daemon step that squashes Dolt history older than 7 days and keeps the last 7 days of commits, nightly after the backup and before the gc, off by default. The first run is manual, with the operator present, and is the 2 GB flatten (docs/dolt-history-offline.md, "When to flatten"). The method is the surgical rebase of docs/design/dolt-storage.md ("Surgical compaction"): a work branch and a swap, never a rebase of main in place.

Related: gt-9fcui (14 nightly backups, landed), gt-hk21d (events retention, landed). With events kept 30 days, `bd history <id> --events` reaches back 30 days; older changes survive only in the nightly backups and the JSONL backup repository's git history.

## Facts (measured 2026-11-01)
gt database: 24,182 commits in dolt_log, 21,951 since 10-26 (3.4k a day), 1.69 GiB on disk by du, post-gc 1.149 GB with oldgen 603 MB, growth +0.10 to 0.15 GiB a day (nightly backup sizes, 10-26 to 11-01). Per commit that is about 31 to 46 KB (0.10 to 0.15 GiB over 3.4k commits a day: arithmetic on those two measured series, not a measured per-commit cost; the whole-database ratios, 1.69 GiB over 24,182 commits about 75 KB and 1.149 GB about 48 KB, include history from before 10-26 and the events table). The history is the issues, comments and labels rows; events and wisps are dolt_ignore'd. Backups: nightly in the 03:00 window. The source keeps 14 nights since gt-9fcui landed on 2026-11-01 (7 before); whether the installed daemon already runs that build is not verified, so until an install the live rotation may still keep 7. A rebase replays the commits in its plan; the cost of replaying about 24k commits is NOT measured and the first manual run measures it.

## Steps (daemon step, per enabled database; first target gt only)
0. Switch: `squash` block under the scheduled-maintenance config, `enabled` false by default, `databases` list, `keep_days` 7, `min_old_commits` (do nothing below it), `max_runtime`. Off means the step is not even constructed.
1. Preconditions, all or skip with a logged reason: inside the window; no gate slot held and no landing pass, sling cycle or install in flight (the gc's own conditions); the daemon's Dolt maintenance mutex acquired; no pause marker held by someone else; THIS NIGHT's backup of the database completed with a manifest naming it (doltbackup.LastFor), finished within the last 6 hours (the same bound for the daemon step and the manual run); free disk at least 2 x the database size; commits older than keep_days exceed min_old_commits.
2. Park writers: write the pause marker (internal/doltpause, reason "history squash", until = max_runtime + slack) and wait until the processlist shows no non-daemon connection writing (bounded wait; skip if it does not clear).
3. Record BEFORE: the main tip hash; for every versioned table the row count (`SELECT COUNT(*)`) and `dolt_hashof_table(t)`; the commit count; the cut commit C = newest commit with date < now - keep_days.
4. Branch: `compact-base` at the initial commit, `compact-work` from main. Any leftover compact-* or main-pre-squash branch from a dead run aborts the step with an escalation (do not delete another run's branches blindly). A database found with `main-pre-squash` or `compact-*` branches is a dead run: tell which state it died in from `SELECT name, hash FROM dolt_branches` and follow "Recovery by swap state" below, then escalate.
5. `CALL DOLT_REBASE('--interactive','compact-base')` on compact-work; `UPDATE dolt_rebase SET action='squash' WHERE rebase_order > (SELECT MIN(rebase_order) FROM dolt_rebase) AND commit_hash IN (SELECT commit_hash FROM dolt_log WHERE date <= <date of C>)`; `CALL DOLT_REBASE('--continue')`.
6. Verify on compact-work: every table's row count AND dolt_hashof_table equal the BEFORE values; the main tip is still the BEFORE tip (no writer moved it); commits in the last keep_days survive one for one (count of commits newer than C unchanged); exactly one commit at or before C remains; the number of `dolt_rebase` rows marked squash equals the commits at or before C minus one, and none is newer than C (so the squashed range is contiguous).
7. Swap, in an order that never leaves the database without a main: (a) `DOLT_BRANCH('-m','main','main-pre-squash')` renames the old main out of the way; (b) `DOLT_BRANCH('-m','compact-work','main')` puts the squashed branch in its place; (c) `DOLT_CHECKOUT('main')`; (d) re-run step 6's counts and hashes on main; (e) only when (d) matches, `DOLT_BRANCH('-D','main-pre-squash')` and `DOLT_BRANCH('-D','compact-base')`. The old history stays reachable as `main-pre-squash` until (e), and the gc of step 9 cannot reclaim it before then. Whether Dolt lets the server's default branch be renamed while clients are connected is NOT verified; the first manual run checks it (R6) and the design changes to a copy-and-reset of the branch pointer if the rename is refused.
8. Unpark: remove the pause marker. Log one summary line: commits before and after, duration, tables verified. Write the result to daemon/maintenance_state.json.
9. The existing gc step then runs (`dolt_gc('--full')`): the squash itself frees nothing until the gc reclaims the old chunks. Record the size before and after the gc.

## Abort conditions (before step 7: drop compact-work and compact-base, remove the marker, escalate high, leave main untouched; from step 7 on follow the recovery table)
a precondition fails after step 2 began; the BEFORE and AFTER row count or table hash of any table differs; the main tip moved during the run; DOLT_REBASE reports a conflict or any error; the run passes max_runtime; the free disk drops under 1 x the database size; the process dies (the marker lapses on its own; the next start finds compact-* branches and escalates, step 4). From step 7 on, the abort is the recovery of the swap state the run is in, "Recovery by swap state" below, not a drop of branches: its table says which branch to rename and in which order, and what proves the original `main` is back.

## Recovery by swap state

This governs a destructive step, so each state names what exists, the exact commands and the check that proves the recovery worked. Find the state first: `SELECT name, hash FROM dolt_branches ORDER BY name;` and compare `dolt_hashof('main')` with the BEFORE tip recorded in step 3. Never delete a branch that holds history until the original `main` is back and checked. Every row ends with an escalation (high; critical from S3 on).

| State | What exists | Commands, in this order | Check that proves it |
|---|---|---|---|
| S0: before (a), steps 3 to 6 | `main` (original), possibly `compact-base`, `compact-work` | If a rebase session is open or died (`SELECT COUNT(*) FROM dolt_rebase` on `compact-work` answers, or docs/dolt-history-offline.md's check says so): `CALL DOLT_REBASE('--abort');` first. Then `CALL DOLT_CHECKOUT('main'); CALL DOLT_BRANCH('-D','compact-work'); CALL DOLT_BRANCH('-D','compact-base');` (the abort rule) | `dolt_hashof('main')` equals the BEFORE tip; `dolt_branches` lists only `main` |
| S1: after (a), before (b) | NO `main`; `main-pre-squash` (original); `compact-work`, `compact-base` | `CALL DOLT_BRANCH('-m','main-pre-squash','main');` then drop `compact-work` and `compact-base` | `dolt_hashof('main')` equals the BEFORE tip; every table's `dolt_hashof_table` equals the BEFORE record; `bd list --limit 1` answers |
| S2: after (b), verification (d) pending or failed | `main` (SQUASHED), `main-pre-squash` (original), `compact-base` | First `CALL DOLT_BRANCH('-m','main','main-squashed-FAILED');` THEN `CALL DOLT_BRANCH('-m','main-pre-squash','main');` (reverse order: the squashed branch is renamed, never deleted, before the original is back); drop `compact-base`; keep `main-squashed-FAILED` until the operator says to drop it | `dolt_hashof('main')` equals the BEFORE tip; table hashes equal the BEFORE record; `main-squashed-FAILED` still exists |
| S3: (d) matched, before (e) | `main` (squashed, verified), `main-pre-squash` (original), `compact-base` | Re-run step 6's counts and hashes on `main` against the saved BEFORE record. If every one matches, complete (e): drop `main-pre-squash` and `compact-base`. If any differs, or the BEFORE record is gone, treat it as S2 (the original is kept) | the saved record and `main` agree on every table before `main-pre-squash` is dropped; after the drop `dolt_branches` lists only `main` |
| S4: after (e) | `main` (squashed, verified); the original history is gone | No branch recovery exists. Restore `gt` from the pre-flatten backup per docs/dolt-restore.md: the nightly `~/gt-backups/dolt/<date>/gt` or the copy taken in the backup plan below, `finished` no more than 6 hours before the run began | the restored `gt` matches the BACKUP's own record, not the BEFORE record (the backup can be up to 6 hours older than the run, so the two differ by every write since): its tip and per-table `dolt_hashof_table` values as recorded when the backup finished (the manifest, or a hash taken on the copy before use); the writes between the backup and the run are not in it, and are replayed from the JSONL backup mirror refreshed in R0 (its 15-minute commits) only on the operator's decision; escalate critical |

Why this order: `DOLT_BRANCH('-m', old, 'main')` fails while a branch named `main` exists, so with both branches present the squashed one must be renamed away first; renaming (not deleting) keeps both histories reachable until the original is checked.

## Test plan
1. Unit, fake SQL executor and injected clock: each precondition skips with its reason; each abort condition runs the cleanup and the escalation exactly once; the sequence of statements is exactly steps 3 to 7, including a process death injected after each statement of step 7, and a restart in each state S0 to S4 of the recovery table, which must end in the table's check; a leftover compact-* branch aborts at step 4; the switch off constructs nothing.
2. Integration, throwaway Dolt container under the gate slot (like the beads recorder tests), narrow `-run`: create 300 commits with `--date` spread over 14 days over three tables; run the step; assert one old commit plus the commits of the last 7 days, identical table hashes, no compact-* branches, main exists; then a second run does nothing (below min_old_commits).
3. Failure integration: a writer commit injected between steps 3 and 6 aborts with main untouched; a table hash forced to differ aborts before the swap.
4. Mutation proofs: drop the hash comparison, drop the pause marker, rebase main directly instead of the work branch, skip the backup precondition; each turns a named test red.
5. Measured in the first manual run, not assumed: rebase time for about 24k commits, peak disk use, whether bd clients honor the pause marker or fail while main is absent during the swap.

## First manual run (the morning the operator chooses; not tied to L3), operator present
Owner of each step in brackets.
R0 [operator, overseer] Pick the time (a window with the fewest seats busy). Refresh the JSONL backup mirror: `git -C ~/gt-backups/dolt-archive-git-mirror-20261101 fetch` (its origin is ~/gt/.dolt-archive/git, the daemon's JSONL git backup repository) and write down the fetched tip. Measure and write down: `du -sh ~/gt/.dolt-data/gt`, `du -sh ~/gt/.dolt-data/gt/.dolt/noms/oldgen`, `SELECT COUNT(*) FROM dolt_log`.
R1 [overseer] Backup: use the 03:00 nightly backup if it finished within 6 hours and names gt (the daemon step's bound; a run later in the morning takes a fresh backup instead) (`~/gt-backups/dolt/<date>/backup.json`); otherwise run the same `dolt backup sync-url` the daemon runs (internal/daemon/maintenance_backup.go maintenanceBackupOne) into a dated directory outside the rotation. Check the restore page (docs/dolt-restore.md) lists the restore steps for this database.
R2 [operator] Dispatch hold: the operator sets `~/gt/seat-refill.hold` (agents never create it); the overseer stops landings and slings, waits for the seats to drain, and tells the birds to stop writing. `gt dolt pause --reason "history squash" --until 90m`. Confirm with the processlist that only the daemon is connected.
R3 [overseer] BEFORE record: for gt, per versioned table `SELECT COUNT(*)` and `SELECT dolt_hashof_table('<t>')`, the main tip (`SELECT dolt_hashof('main')`), the commit count, and the time of the cut commit. Save them in ~/gt/.runtime/overseer/squash-before.txt.
R4 [overseer] The SQL of steps 4 to 5 in a dolt sql session against gt, keeping the session open between statements (the rebase state lives in the session): compact-base, compact-work, the interactive rebase, the UPDATE on dolt_rebase with the 7-day cut, the --continue. Time it. On any error: `CALL DOLT_REBASE('--abort')`, checkout main, drop both branches (docs/dolt-history-offline.md), unpause, stop here.
R5 [overseer] Verify as in step 6 against the R3 file. Any difference: abort as above. Only an exact match goes on.
R6 [operator present] Swap (step 7 (a) to (e)); check at (a) whether the rename of the served default branch is accepted and note the answer; repeat the verification on main before (e), then `bd list --limit 1` from a rig directory and `bd show` of two known beads.
R7 [overseer] `gt dolt unpause`; the operator removes the hold; the seats resume. Watch one dispatcher tick and one landing.
R8 [overseer] gc: either wait for the 03:00 window (the old-gen growth rule may not fire after a rewrite, so run it by hand) or, under a fresh pause marker, `CALL dolt_gc('--full')` once; record du and oldgen before and after. Expect the oldgen to drop towards the size of the last 7 days of history (the target to compare against: post-gc 1.149 GB today).
R9 [overseer] Record the measured numbers (rebase duration, disk peak, commits before and after, size before and after) in docs/design/dolt-rolling-squash.md and on this bead. Rollback if something is wrong during R4 to R6: follow "Recovery by swap state"; only after step 7 (e) is the restore from the backup of R1 (docs/dolt-restore.md) the way back.

## Backup plan for the first run

Where the copies sit (docs/dolt-restore.md, "Where the backups are written"): the Dolt server runs in the `gt-dolt` container on the Mac and writes each night under `~/gt-backups/dolt` through its bind mount. The daemon in the pod mounts the same Mac directory as a hostPath and sets `GT_DOLT_BACKUP_ROOT` to it. The daemon, not the server, renames `<date>.partial` to `<date>`, writes `backup.json`, and keeps the newest 14 nights; rotation removes only dated nights and `.partial` directories under that root, so a copy made under step 2 must not take either name there.

1. The restore path is docs/dolt-restore.md; read it before the run and confirm the nightly backup of the day holds the database: `cat ~/gt-backups/dolt/<date>/backup.json` lists `gt` and `finished` is under 6 hours old, the daemon step's bound. The source keeps fourteen nights (gt-9fcui, landed 2026-11-01; the installed daemon may still keep seven until the next install), so the night before the run is still there after the run either way.
2. If the nightly backup is older than 6 hours, take one by the daemon's own method into a directory outside the rotation (so Rotate never removes it): `CALL dolt_backup('sync-url', 'file://<dir>/gt')` through the running server (internal/daemon/maintenance_backup.go, doltBackupSyncURL), under a pause marker (`gt dolt pause --reason "pre-squash backup" --until 30m`, then `gt dolt unpause`).
3. Check the copy is whole before going on: its `du` is within 10% of the database's backup size of the night before (1.22 GiB for gt in the 2026-11-01 nightly backup, du of ~/gt-backups/dolt/2026-11-01/gt, measured 2026-11-01; the other nights are 0.34 to 1.09 GiB, 10-26 to 10-31), and the COPY itself is read, not the source: clone it into a scratch directory (`dolt clone file://<dir>/gt <scratch>`, docs/dolt-restore.md) and compare there `dolt log -n 1` and `SELECT dolt_hashof_table('issues')` with the tip and hash recorded for that backup (a backup taken under the pause marker in this plan: the BEFORE record; a nightly one: its manifest, since the source has moved on since).
4. Keep the pre-run copy until the squash has run for a week.
