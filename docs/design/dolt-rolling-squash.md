# Rolling Dolt history squash

Before changing anything about the squash, read the v2 design. It replaces the runbook this document held (the daemon step, the first manual run and its backup plan) with an automatic run: no drained town, no dispatch hold, and the swap verified and renamed by the machine. Its "What stays and what goes" table names each data-safety rule the run keeps. Its plan is [2026-11-15-dolt-squash-plan.md](../plans/2026-11-15-dolt-squash-plan.md). The offline flatten and the surgical rebase SQL stay in [docs/dolt-history-offline.md](../dolt-history-offline.md).

One correction to the steps this document held: inside a rebase session `dolt_log` shows only the base, so a plan filter of `commit_hash IN (SELECT commit_hash FROM dolt_log WHERE date <= cut)` selects no row and every commit stays a `pick`. The filter source is `dolt_log('main')`, as measured on scratch databases and recorded in the v2 design, "Why it changes".

Related: gt-9fcui (14 nightly backups, landed), gt-hk21d (events retention, landed). With events kept 30 days, `bd history <id> --events` reaches back 30 days; older changes survive only in the nightly backups and the JSONL backup repository's git history.

## Facts (measured 2026-11-01)
gt database: 24,182 commits in dolt_log, 21,951 since 10-26 (3.4k a day), 1.69 GiB on disk by du, post-gc 1.149 GB with oldgen 603 MB, growth +0.10 to 0.15 GiB a day (nightly backup sizes, 10-26 to 11-01). Per commit that is about 31 to 46 KB (0.10 to 0.15 GiB over 3.4k commits a day: arithmetic on those two measured series, not a measured per-commit cost; the whole-database ratios, 1.69 GiB over 24,182 commits about 75 KB and 1.149 GB about 48 KB, include history from before 10-26 and the events table). The history is the issues, comments and labels rows; events and wisps are dolt_ignore'd. Backups: nightly in the 03:00 window. The source keeps 14 nights since gt-9fcui landed on 2026-11-01 (7 before); whether the installed daemon already runs that build is not verified, so until an install the live rotation may still keep 7. A rebase replays the commits in its plan; the cost of replaying about 24k commits was NOT measured on 2026-11-01.

## Recovery by swap state

The v2 design's "Recovery by state" names the state and the branch to restore; this table keeps the exact commands and the check that proves the recovery worked. The record every check compares against is the BEFORE record, taken before the swap: the main tip, each versioned table's row count and `dolt_hashof_table`, and the commit count (v2 design, step 3). Find the state first: `SELECT name, hash FROM dolt_branches ORDER BY name;` and compare `dolt_hashof('main')` with the BEFORE tip. Every row ends with an escalation (high; critical from S3 on).

| State | What exists | Commands, in this order | Check that proves it |
|---|---|---|---|
| S0: before the swap | `main` (original), possibly `compact-base`, `compact-work` | If a rebase session is open or died (`SELECT COUNT(*) FROM dolt_rebase` on `compact-work` answers, or docs/dolt-history-offline.md's check says so): `CALL DOLT_REBASE('--abort');` first. Then `CALL DOLT_CHECKOUT('main'); CALL DOLT_BRANCH('-D','compact-work'); CALL DOLT_BRANCH('-D','compact-base');` | `dolt_hashof('main')` equals the BEFORE tip; `dolt_branches` lists only `main` |
| S1: after the first rename, before the second | NO `main`; `main-pre-squash` (original); `compact-work`, `compact-base` | `CALL DOLT_BRANCH('-m','main-pre-squash','main');` then drop `compact-work` and `compact-base` | `dolt_hashof('main')` equals the BEFORE tip; every table's `dolt_hashof_table` equals the BEFORE record; `bd list --limit 1` answers |
| S2: after the swap, its verification pending or failed | `main` (SQUASHED), `main-pre-squash` (original), `compact-base` | First `CALL DOLT_BRANCH('-m','main','main-squashed-FAILED');` THEN `CALL DOLT_BRANCH('-m','main-pre-squash','main');` (reverse order: the squashed branch is renamed, never deleted, before the original is back); drop `compact-base`; keep `main-squashed-FAILED` until the failed verification is explained | `dolt_hashof('main')` equals the BEFORE tip; table hashes equal the BEFORE record; `main-squashed-FAILED` still exists |
| S3: swap verified, before the old history is dropped | `main` (squashed, verified), `main-pre-squash` (original), `compact-base` | Re-run the BEFORE counts and hashes on `main` against the saved record. If every one matches, drop `main-pre-squash` and `compact-base`. If any differs, or the BEFORE record is gone, treat it as S2 (the original is kept) | the saved record and `main` agree on every table before `main-pre-squash` is dropped; after the drop `dolt_branches` lists only `main` |
| S4: after the old history is dropped | `main` (squashed, verified); the original history is gone | No branch recovery exists. Restore `gt` from the nightly backup per docs/dolt-restore.md: `~/gt-backups/dolt/<date>/gt`, `finished` no more than 6 hours before the run began | the restored `gt` matches the BACKUP's own record, not the BEFORE record (the backup can be up to 6 hours older than the run, so the two differ by every write since): its tip and per-table `dolt_hashof_table` values as recorded when the backup finished (the manifest, or a hash taken on the copy before use); the writes between the backup and the run are not in it, and are replayed from the JSONL backup repository (its 15-minute commits) only on the operator's decision; escalate critical |

Why this order: `DOLT_BRANCH('-m', old, 'main')` fails while a branch named `main` exists, so with both branches present the squashed one must be renamed away first; renaming (not deleting) keeps both histories reachable until the original is checked.
